01What a mod actually is here

A mod is a folder the game reads on startup. The Studio writes it for you, and it contains a small set of cooked files:

<game>\SWZeroCompany\Mods\YourMod\
    YourMod.uplugin
    AssetRegistry.bin
    Content\Paks\YourMod_P.pak
    Content\Paks\YourMod_P.ucas
    Content\Paks\YourMod_P.utoc

The game's own mod runtime finds that folder and mounts it at a higher priority than the base game, which is what lets a mod add parts and replace assets. Nothing belonging to the game is overwritten on disk. For almost every mod that folder is the whole mod, and removing it removes the mod completely.

The exception is a mod that changes one of a short list of the game’s own files that the game reads before it looks at the Mods folder. A change to one of those cannot live in the folder, so the Studio puts it in SWZeroCompany\Content\Paks\~mods for you, as YourMod_Early_P.pak, .utoc and .ucas, and the rest of the mod stays in Mods\YourMod. Such a mod has two places to remove, not one. A mod with a second half has the list and the rules.

There are two kinds of thing you can put in one:

KindWhat it does
PartAdds something new to the game — a helmet, a torso, a specialisation. Built by copying an existing part and changing it.
OverrideShips a changed copy of one of the game's own assets under its own name. This is how a locked specialisation or weapon gets opened up.

Most of what you will do is parts. Overrides have a section of their own, and so does editing an asset’s properties directly.

02First run and the window

The first time you open the Studio it looks for your Zero Company install by itself and shows you what it found in a small window: press Use this install. If it found more than one, the first is already chosen and the others are one click away; if it found none, press Browse… and point it at the folder containing SWZeroCompany. It then reads the data-layout file it ships with and remembers where the game is. That is asked once — and not at all when you update by unzipping a new version over the old folder, which keeps its answer. If the game is later moved or uninstalled, the Studio asks again rather than quietly choosing something else.

To change the answer yourself — the game moved, or you want the other of two installs — use Project → Find the game again…. The answer is saved in the settings folder beside the Studio, and the Blender add-on and the command line use the same one.

Every launch after that it checks the game against the file it ships with, and if the game has been patched past it, shows a window saying so with one button, Carry on anyway. That warning matters: the tool reads the game's data through that file, and against a newer build it does not fail — it reads wrong values, silently. If you see it, expect names, icons and slots to be unreliable until a new one is available. The window says where to look: the About menu's Downloads and updates opens the page where new versions of the Studio are published.

The window

Four menus sit across the top — Project, Edit, Handbook and About — and a fifth, Plugins, appears when the Studio carries an add-on or a preset to offer (the Blender add-on, the Substance preset, the 3ds Max script). Project is where a mod is created, unloaded, built and taken back out of the game, and where you tell the Studio again where the game is (Find the game again…); Handbook is how you got here; About names the version and the author and has the update check.

Under them is the tab strip, and it holds two different kinds of tab side by side. The first thirteen never close: they are the sections, one per kind of thing you can change.

Under the strip the window is in two halves. On the left is a list: the Data Explorer's folder tree with the files of the folder you pick beneath it, or, when a section is open, that section's rows with their own filter box. On the right is whatever the open tab is — the 3D viewport for a model, the image for a texture, an editing sheet for a part, and for any other asset its Properties grid.

The 3D viewport

Open any model and it draws. Drag to orbit, and the toolbar above it carries Grid, Floor and Shadows toggles, an Lod picker, a View Mode list that shows one channel of the shading at a time, and Export, Import and Tint.

Down its right side are four side tabs. Properties is the asset's own fields, in the same grid that a double-click in the Data Explorer opens (section 20). Animations lists every sequence that will actually play on the loaded rig, grouped by weapon set and then by action — a torso fits a few thousand of them, so the groups fold. Meshes hangs other pieces on the loaded one, which is how you see a whole trooper rather than a floating torso. Materials is what it is painted with.

Right-click the row and choose “Find in Data”. It lands on that asset in the Data Explorer, wherever it really lives. That is the answer — you do not need to know the path.

The rest of this is why, and only worth reading if you are curious. There is a node at the top of the tree named after each installed mod, and it is almost empty: the plugin descriptor, a registry, three small files, none of your artwork. You can preview it

Click the mesh and it loads in the viewport like any game asset — your own copy, with your own textures on it. That is a real read-back of what you shipped, not a preview of what you asked for, so it is worth doing before you launch the game.

Reload after installing

Containers are mounted once, at startup. A mod you have just built and installed is not in the tree until the game is read again — restarting the Mod Studio. Without that it looks like the install did nothing.

It looks for updates, and you can stop it

Once per run the Studio asks GitHub whether a newer release exists, and says so beside the credit in the menu bar if there is one. It sends nothing about you or your mods — it reads one public page and compares a version number. About → Look for a newer version when this starts turns it off, and it stays off.

  1. Find it in the Clothing section Type into the filter — a name, a character, a word from the menu. Each row shows the game's own thumbnail, so you are looking at the same picture the game shows you.
  2. Right-click it and choose “Duplicate” This puts a copy in your mod. It carries across the mesh, the icon, the slot, whether a helmet hides the head, and — importantly — the original part as its template.
  3. Your copy opens in a tab of its own You land in it straight away; there is nothing to accept. A duplicate has to go somewhere, so if you have no mod open yet, make one first with Project → Create New Mod.
  4. Change what you want At minimum give it a name people will see in the menu. Everything else has a sensible default.
  5. Build and install One press writes the files, reads them back, and installs only if that read-back was clean. Building, and what the check catches says what the check looks for.
Finding things in a list of eleven hundred

The Clothing list is grouped into fold-away sections, in the order you would dress a character — Headwear, Tops, Armwear, Lower body, Boots, then everything else. Collapse all puts the whole catalogue on one screen, which is the fastest way to see what kind of thing exists before you go looking for one.

Where a name is genuinely ambiguous the row says why. Six entries called “ARC Trooper Phase II” are the same helmet in different colourways, and each row carries the part of its asset name that differs — base, TintA, TintB — so you can tell them apart without opening each one.

Why the template matters

A part is more than a mesh. It carries a base class and a set of fragments — the voice filter, the ability list, the attribute tables. Copying the part you picked keeps all of that. An earlier version of this tool took only the mesh and then guessed at a base, and a clone helmet came back built on a Mandalorian part: right geometry, no clone voice filter. Duplicating it sets the template for you, which is why it is better than adding a blank part and filling in a mesh path.

04Worked example: Rex's armour for everyone

This is the thing most people want first, and it is worth explaining why it works, because the reason is not what most people assume.

Captain Rex's armour exists in the game as six ordinary outfit parts:

CPD_H_Outfit_CaptainRexA_HELM     Helmet
CPD_H_Outfit_CaptainRexA_TORS     Torso
CPD_H_Outfit_CaptainRexA_ARMS     Arms
CPD_H_Outfit_CaptainRexA_LEGS     Legs
CPD_H_Outfit_CaptainRexA_BOOT     Boots
CPD_H_Outfit_CaptainRexA_PACK     Pack
The key fact

Those parts are not locked to Rex. They carry no character restriction at all. What keeps them out of your menu is a development gate — and a copy does not inherit that gate, because the copy is registered under its own name with the gate tags stripped. So duplicating them is genuinely all it takes.

Which makes the recipe short:

  1. Create a mod Project → Create New Mod → type a name (say RexArmour) → Create.
  2. Filter the Clothing section for CaptainRexA All six pieces come up together.
  3. Right-click each one and choose “Duplicate” One at a time. Six parts, six times. Each lands in your mod with its slot and mesh already correct, and opens in a tab of its own.
  4. Name them for the menu They default to “… (Mod)”. Something like “501st Captain — Helmet” reads better in game.
  5. Build and install Then start the game and look in the armoury. Every humanoid character can wear them — Hawks included — because nothing in the copy says otherwise.

Parts that are locked to a character

Some parts genuinely are restricted — heads, hair, and hero gear kits. Hawks has 32 such parts, Tel-Rea 24, Cly 16. They carry a name tag like br.Customization.Part.Character.Info.Name.CaptainRex, and a copy does inherit it. The build tells you when that happens:

CPD_Mod_Something: restricted to CaptainRex
                   by the template it was built from

Stripping that tag is what frees the part, and the part editor’s TAGS card is for exactly this. It lists the tags the template actually carries, each with a tick, so you untick the name tag out of a list rather than typing fifty characters of dotted namespace. The build then confirms it: “unlocked for everyone”.

Going the other way

For character restricts a part to one person. Choosing a name writes that character's tag onto the copy and takes any other one off, so it means exactly them. Leave it on everyone unless you specifically want a piece only one character can wear.

These are separate

Setting For character to everyone does not remove an inherited restriction — it just does not add one. If your copy came from a hero's own gear, untick their name tag on the TAGS card to take it off.

05The part editor, field by field

Duplicate a part and its tab opens as a rail of sections down the left, headed WHAT YOU CAN CHANGE, with a card for each on the right. Click a section and the page scrolls to its card; each card folds shut. A part shows only the cards it has — a helmet has no ability swap, a specialization has no mesh — and a dot beside a section marks a change you have not saved. Under the title the tab says your own copy of the part you copied: that is the template, set for you when you duplicate.

Along the bottom of the sheet a bar counts what you have changed and carries Undo all of it, Stop editing and Save changes.

06Importing your own mesh

In the part editor, open the MESHES card. There is a row for each mesh the part wears, and on the row Import… opens a file picker for your FBX. The Studio copies the file into ModSource\<your mod>\Meshes beside your mods — the folder is created for you — and the row says your own mesh from then on. Pick… on the same row points it at another of the game’s meshes instead, View opens whatever it wears in the 3D tab, and Revert gives the game’s back.

Requirements

  • Binary FBX. Not ASCII.
  • Skinned to the bones the part already uses. A weight on any other bone is dropped, and the build tells you which bones it dropped.
  • Keep the part's slot. A torso mesh in a helmet slot will equip in the helmet slot and look exactly as wrong as that sounds.
Why the bone list matters

Every humanoid part in this game is skinned to the same skeleton. That is what makes Rex's torso wearable by Hawks in the first place, and it is what makes your own mesh wearable by anybody — provided you weighted it to bones that exist on that skeleton. Export the part you are replacing first, use its rig as your reference, and the weights land where the game expects them.

Heads keep their facial animation — if you keep the vertex count

A head is not like the other slots. Beside its geometry it carries several hundred morph targets: the per-vertex deltas that are every expression the character can make. They are stored as compressed deltas addressed by vertex number, which means they only make sense against the exact vertices they were built for.

So the Studio applies one rule, and it is worth designing around:

  • Same vertex count as the head you started from — the expressions are carried through untouched. This is what you get if you export the head, move its vertices about, and bring it back. The face still acts.
  • Any other count — the deltas would point at vertices that no longer exist, so they are dropped. The head renders correctly and is completely still. The build says so in as many words; it is never silent.

If the face matters, edit the vertices of an existing head rather than modelling a new one. Adding or removing a single vertex costs you every expression, and nothing about the result looks wrong until the character tries to speak.

Only the closest level of detail carries expressions, in the game's own heads as much as in yours — so a face that stops animating at a distance is the game working normally, not your mod.

Importing a mesh makes your mod carry its own copy of that mesh automatically, because your geometry has to live somewhere and it is not going in the game's files.

Garments that are several pieces

Some clothing dresses more than the slot it sits in. Clone Commando armour is one part, in the Torso slot, and wearing it replaces your boots, legs and arms as well — and adds a backpack. Inside, that part is not one mesh but five, one per body region, and it takes over the other slots so nothing you had chosen shows through.

When you open a part like that, the MESHES card has a row for each piece — BOOT, TORS, PACK, LEGS, ARMS — and the SLOT card lists the slots it takes over, each with a tick. HOW IT FITS gets a Piece picker once more than one piece carries an import, so you place one piece at a time. Every piece starts out pointing at the game's own mesh, so a freshly duplicated garment is the garment you picked, unchanged. Press Import… on a row to give that piece your own file.

A piece you leave alone keeps the game's geometry. Replacing one piece of five is one row, not five. If you only want to redo the backpack, import into the PACK row and leave the rest.

One garment, one entry — or several parts?

A garment like this is one part in one slot, so the game gives it one name and one picture however many pieces it wears. It takes over the other slots and greys them out, so those have nothing to name. The game's own Clone Commando is built exactly that way.

That is a choice rather than a limit, and the other option is worth knowing:

To build the second, do not use the whole-body template at all: copy the game's own per-region parts instead — there is a separate Boots, Legs, Arms and Torso part for each armour kit — and give each one its own name, icon and mesh.

Give every piece the same scale and axes. A model split across several files is aligned in your modelling tool and exported from one scene — the pieces have no offset relative to each other here, so if they line up in Max they line up in game, and if they do not, they will not — unless you give a piece a Move (cm) of its own on HOW IT FITS.

If a project names a piece the template does not have, the build refuses to guess — an entry aimed at nothing is never quietly applied to some other piece.

Extracting a whole folder

Right-click any folder in the Data Explorer and choose “Extract this folder”. A window opens showing what is in there before it asks you for anything — the file count and the breakdown by kind, because these folders run from four assets to fourteen thousand and that is the whole decision.

Then pick where it goes and in what formats: a mesh format, a level of detail, how Nanite geometry is treated, a texture format, and whether materials and morph targets come with it. Those start from the same settings the Export panel and the command line use, so a format chosen anywhere is the format all three write — but changing them here is for this run only and does not move the shared answer.

FBX comes out the right way round. The game works in a left-handed space and every FBX the Studio writes — a dump, the Export button on a model’s 3D tab, the Export panel, and this folder run — declares a right-handed one, so a straight copy of the game’s numbers would open in Blender as a mirror image of the model, turned inside out. The Studio converts the whole file for you — the mesh and its normals and, for a character, every bone, the skin and the bind pose together — so a dumped model is not a mirror image of the game’s, its faces point outward, and its skeleton still holds the skin at rest, in Blender and in 3ds Max. Export your edit from Blender with the default settings, bring it back with Import…, and it lands the same way round. PSK and glTF are written as they always were. An animation asked for in an FBX dump still comes out as a .psa (ActorX), which belongs with the PSK form of the same character (3ds Max’s ActorX importer), not with the FBX.

Everything at or below the folder is written out with the tree recreated underneath, exactly as the Data Explorer shows it. The remaining-time estimate appears once the run has earned one, about twenty assets in; a folder of Nanite meshes and a folder of icons are orders of magnitude apart, so there is no useful figure to quote before then. The same button stops it, and a run stopped part way keeps what it already wrote.

Assets that cannot be exported are named rather than counted — a Skeleton, for instance, has no standalone export and arrives with its mesh instead. “One failed” with no reason is a number nobody can act on.

Getting the game's models into Blender

Before you can replace a mesh you need the original to work against — its shape, its scale, and above all its rig, because your model has to be weighted to bones the game already has. The Blender add-on that ships with this tool does that from inside Blender: browse the game, click an asset, and it arrives in your scene with its skeleton, its skin weights and its materials already set up.

The installer is in this Studio, under Plugins → Add-ons and presets…. It finds every Blender on the machine (4.2 or newer), shows what is installed in each, and its Install button copies the add-on into place and tells the add-on where this Studio is. Blender itself asks you to switch it on the first time — open Edit › Preferences › Add-ons, search for Zero Company, and tick it. That last step cannot be done for you; Blender keeps its list of enabled add-ons inside its own preferences file. If the window says No Blender found, open Blender once and press Rescan: Blender is found by its settings folder, which it makes the first time it runs.

Updated from 1.6.x, and imports from Blender stopped working? The add-on that version installed runs a program this version no longer includes, so every import fails with just “The exporter failed”. You do not need to do anything but look: when the Studio starts it notices an add-on that is older than the one it ships, and a bar under the menu offers Update the Blender add-on — one click. It replaces the add-on’s own folder and changes nothing else. Blender can stay open while that happens, but restart it afterwards: it keeps the old add-on in memory until it does, and switching the add-on off and on is not enough. The add-on stays switched on, so there is nothing to tick again. The Studio also removes the old program’s files (UEToolkit.App.*, version 1.x) from its own folder, and says in the Log which ones.

The same window carries two more things that ship beside the Studio: the Substance 3D Painter export preset, and a 3ds Max script for porting a character from another game onto this game’s rig (it was written for one source rig, and its file name says which). Each is one file, and the button asks where to put it.

Then, in Blender, press N in the 3D viewport to open the sidebar and pick the Zero Company tab.

Imported before 1.3? Import it again

Every import made before version 1.3 arrived with its skeleton upside down — the spine running downward out of the hips and the feet finishing above the shoulders. The model itself was always correct, which is why it was easy to miss, and skin weights were never affected. Nothing is wrong with your file; re-import the asset on 1.3 and the armature comes in the right way up.

  1. Scan Game, once. It reads what the game contains and remembers it, so the list is instant from then on.
  2. Pick a category — Characters, Weapons or Vehicles — and narrow it further by collection if you want, or just type in the search box.
  3. Import Selected. A couple of seconds later the model is in your scene.

What arrives is the real thing: the mesh, an armature with the game's own bone names, the vertex groups that bind them, and materials with the game's textures already connected. Export your edited version as FBX and bring it back with Import… on the MESHES card above.

Two textures come in switched off on purpose. The mask and the tint mask are loaded onto the material and left unconnected, labelled with the names the game uses for them. They pack several different things into one image, and wiring them up as though they were ordinary maps would look right and be wrong. They are there for when you know what you want from them.

Level scenery is left out of the list. It is four fifths of everything in the game, none of it is what somebody opens this to get, and the pieces are very heavy.

07Replacing textures

Open the TEXTURES card of the part editor. It lists the textures this part actually wears, read from the mesh's own material — not a guess, and not a list of every texture in the game.

  1. Choose a mesh first The material is what names the textures, so until there is a mesh there is nothing to list.
  2. Pick the slot you want to change Each row shows the texture's name, its size and its format. Hover for the full details.
  3. Point it at your own image Press Import… on that row to copy an image in. Pick… chooses another of the game's textures, Use… one already in your mod, and Revert gives the game's back. Leave a row alone to keep the game's own.
Match the shape

Keep your replacement the same dimensions as the original unless you know why you are changing them. The size and format are shown on each row precisely so you can match them.

08Icons

On the ICON card press Pick…. The popup has two halves:

  • Your own icons, with an Import a PNG or TGA… button. That copies the file you choose into ModSource\<your mod>\Icons beside your mods, creates the folder if it does not exist, and selects it. The Import… button on the card itself does the same. You never have to find the folder yourself.
  • The game's own — a grid of the actual pictures, not a list of names, filtered to the slot you are working in.

Duplicating a part brings its icon with it, so this is optional. Change it when you have changed the look enough that the original picture would mislead.

09Building, and what the check catches

One button, Build and install — bottom right, and under Project: the mod is built in a scratch location you never see, read back and checked, and — only if it came back clean — written into the game's Mods folder as its own mod folder. The Log says where it went. If the check fails, nothing is installed. If the game is running and holding its old copy open, the build is checked but not installed, the Log says that something has the file open, and pressing Build and install again once the game is closed finishes the job.

The bar along the bottom has a lamp and a line beside it: Ready, or N things need fixing when the project cannot build yet. The Log names each of those in red, and the button stays off until the count is zero, the mod has something in it and the game is mounted.

Before anything is installed the tool reads back out what it just wrote and inspects it. That read-back is not a formality — it is the difference between a mod that works and one that installs cleanly and does nothing.

What it checks

  • Unlocked for everyone. A gate inherited from the template means the player will never see the part.
  • Offered to every character. An inherited character restriction, reported unless you said you expected one.
  • Carries a slot tag. Without one, nothing will offer it.
  • Registered under its own name. A part registered under another asset's name collides with it and loses — which looks exactly like a mod that never installed.
  • Takes over everything its template does. A missing override slot means the part half-equips.
  • That each edit is really in the built file. For every kind of change your project makes — a typed value, a renamed name, an added tag, a new slot, an array entry — the Log has a line saying it was read back out of the built file: its values read back, its added tags read back, its slots read back. An edit that did not land fails the build; it is never reported as clean.
  • That both halves of a split mod arrived. For a mod with files in ~mods (A mod with a second half): the early container mounts, and delivered early, which names every early file and fails if one is missing from the early container or also sits in the main one.
The gate this gives you

A mod that does not read back clean is not installed. The check runs before the install, every time; if it fails, the Log says the mod was NOT installed and the faults are listed above that line. Build and install itself is greyed while the bar counts things that need fixing — read the line beside it, and the red lines in the Log, because they already say what is wrong.

10Installing and removing

Close the game first. A running game holds its files open and the install will not go through. The Studio says so in the Log and leaves the old copy alone.

Press Build and install. The Studio finds the game's own Mods folder, writes your mod's folder into it, and tells you where it went. Nothing belonging to the game or to another mod is touched, so your mod can sit beside anyone else's. If the mod changes one of the few files the game reads before it looks at the Mods folder, the Studio also writes a second, smaller container into Content\Paks\~mods — A mod with a second half, below.

Project → Take it back out of the game removes it again, completely — from both places, if there are two.

Once it is installed, Zip it for sharing (bottom right, and under Project) packs it for somebody else: What to put in the zip says what it makes.

To look at what you just installed, restart the Mod Studio and then find it in the Data Explorer under Customizations/Mods/. There is no reload: the game's containers are mounted once at startup and the tool holds them read-only for the rest of the session, so a mod installed while it is running is not in the tree it is showing you.

Two mods, one registry

If another installed mod ships its own asset registry, only one can win — and the winner has no record of the other's parts, so one mod's parts vanish entirely from the game. The install says so when it happens. Remove one, or rebuild the other after this one.

A mod with a second half

Almost everything in the game is read when something asks for it, and that is after the game has mounted the Mods folder. A few files are different: the game reads them first and never again, so a copy of one in the Mods folder is mounted and then never looked at. For those files, and only those, the Studio does something else. It builds the changes to them into a second, smaller container — YourMod_Early_P.pak, .utoc and .ucas — and installs it into SWZeroCompany\Content\Paks\~mods, which the game reads before anything else. Everything else stays in Mods\YourMod as before: the new parts, the copies, the registry and every other override.

There is nothing to switch on. If your project changes one of the files below, Build and install splits the mod by itself; if it changes none of them, the mod builds and installs exactly as it always did. The bar along the bottom names both places before you build — SWZeroCompany\Mods\YourMod and Paks\~mods\YourMod_Early_P — and hovering over it says why, and the line that appears when the install finishes says the same. What the Studio checks and refuses

  • An early file may not import something your own mod builds. A part or copy of yours is not mounted yet when the early file loads, so the file would point at nothing. The Log says <file>: loads before mods are mounted, but imports <package> from this mod -- that package is not mounted yet at startup, the change is skipped, and the build is not clean. A slot’s default that names your own part is fine: that is looked up later.
  • A mod whose name ends in _Early is refused. YourMod_Early_P is the name the Studio gives the second half, and it would mistake the two. The bar counts it (“1 thing needs fixing”) and the Log says <name>: a name ending in "_Early" is reserved for the files a mod installs into ~mods -- rename it.
  • Both containers are read back (the last two checks in Building, and what the check catches), and the install is refused while the game holds either half open, in the same words as for the Mods folder: Built and checked, but not installed: something has … open.
  • A rebuild with no early file removes the old one. Otherwise the previous build’s copy would go on overriding the game’s file. The Log says removed the stale early file … -- this build has none.
  • The clash check reads ~mods too. Two mods that change the same early file cannot both win, and which one the game picks is not known, so the Studio warns and names the other mod.

These checks have been run against built files and a test copy of a game folder. None of them has been through a play session.

Taking it out

Remove both places

Project → Take it back out of the game removes a mod from both places, and still works when the ~mods files are already gone. By hand it is two deletions: the mod’s folder from SWZeroCompany\Mods, and YourMod_Early_P.pak, .utoc and .ucas from SWZeroCompany\Content\Paks\~mods. Delete only the folder and the early files stay behind, still overriding the game’s file.

Do it in the game first: unequip anything from the mod and save, then close the game.

A saved character remembers the mod

An existing character keeps the outfit it was saved with, so a new category on the Outfit wheel reaches new characters only. A character made with such a category holds a reference to the mod’s container, and what the game does when that mod is removed is still an open test. Back up %LOCALAPPDATA%\SWZeroCompany\Saved\SaveGames before you remove a mod your characters use, and unequip and save first.

After a game patch, rebuild

An early file is a copy of the game’s file as it was when you built. Once a patch changes the original, your copy is stale — and a stale Outfit wheel affects every new character, not only yours. Rebuild after every game patch. That follows from what an early file is; it has not been measured.

Steam “verify” may take them

After Steam’s Verify integrity of game files, check that the files are still in Content\Paks\~mods, and press Build and install again if they are not. Whether verify touches that folder has not been measured.

“Can I just drop the pak in ~mods?”

This is the first thing most Unreal modders try, because it is how nearly every other UE5 game takes a mod. It is worth knowing exactly what happens, because the honest answer is not simply “no”.

A mod built here is a folder, and it goes in SWZeroCompany\Mods\. The three container files inside it are part of that folder — they are not a mod on their own, and pulling them out to put somewhere else takes the mod apart. The one exception is the Studio’s own early files, above: they are built for ~mods, and they carry no registry, so they cannot clobber anyone’s.

Two ways this goes wrong

A lone .pak never mounts — anywhere. The .pak, .ucas and .utoc are one container in three files. Copy only the .pak, as people do out of habit from older games, and nothing loads at all. That is true in ~mods, in Content\Paks and in the Mods folder alike.

Two mods in ~mods clobber each other. A mod in that older shape has to carry a copy of the whole game's asset registry with its own entries added, and every mod writes it to the same path. Install two and only one registry survives — so the loser's parts are completely absent from the game while its files sit there looking perfectly installed. Nothing announces it.

That second point is the whole reason for the folder. A mod in Mods\ carries its own small registry inside its own folder and shares nothing with anybody, so ten can be installed at once and none can stand on another. The container is still marked _P, so an override still wins against the game's own files — you give up nothing by using it.

Tell the people who install your mod. They will reach for ~mods too. For a mod with no early files, “Unzip the folder into SWZeroCompany\Mods” is the whole instruction, and it saves the message that begins “I installed it and nothing happened”. A mod with early files has two places to arrive, and goes into SWZeroCompany itself: What to put in the zip has both.

11Sharing your mod, and what that protects

Once your mod is a folder somebody else can install, it is worth knowing exactly what you have handed them. The short version: the contents are readable, and nothing here changes that. Everything below is the detail behind that sentence, because a modder deciding how much work to put into a piece deserves the real answer rather than a comfortable one.

What to put in the zip

The Zip it for sharing button packs the mod for you: bottom right, beside Build and install, and under Project. It is live once the mod is installed in your game (until then it is greyed, and hovering over it says why), because it zips what is installed and not what is in your project, so that what you share is what you tested. It writes YourMod.zip beside your project file, says how big it is in the bar at the bottom, lists every file it packed in the Log, and opens Explorer with the zip selected. A HOW TO INSTALL.txt goes into the zip with the mod, so whoever downloads it is told where it goes and how to take it out again.

What goes in the zip depends on whether the mod has a second half in ~mods (A mod with a second half), and the button works that out for you: its tooltip tells you which kind of zip you will get, and so does the line it prints afterwards. You can also tell yourself: the install lines in the Log said N game file(s) load before mods are mounted, and YourMod_Early_P.pak, .utoc and .ucas are in SWZeroCompany\Content\Paks\~mods. All three early files, or none

The .pak, .utoc and .ucas are one container in three files, in ~mods as everywhere else. A copy that has only some of them mounts nothing, and the game quietly uses its own file.

There is no way to encrypt a mod

Unreal can encrypt the containers a game ships. It works by looking up a key that was built into the game's own executable, and Zero Company shipped without one — nothing in the game is encrypted, so there is no key for a mod to use. A mod cannot add one either: registering a key means running code inside the game, which is exactly the kind of thing this tool exists to avoid needing.

An encrypted mod would therefore not be harder to open. It would fail to load.

And the idea does not survive even if the key existed. The game has to decrypt your mod in order to draw it, on the machine of the person you are protecting against — so the key travels with the content wherever it is kept. That is true of every game, not only this one. Free tools already read this game's files, and they will read your mod's the same way.

What the Mod Studio does about it

It refuses to be the easy path. That is a smaller claim than protection and it is the one that is actually true.

The studio shows every mod installed beside the game, so you can see what you have. A mod it did not build is shown with a padlock and a dimmed name, and three things are turned off for it:

What is refusedWhat happens instead

Somebody determined to take your mesh will still take it, with a tool that has nothing to do with this one. What this stops is the easy version — the person who installed your mod, opened the official editor, saw your work in the tree and pressed a button. That road is short, and it is the only one anybody here can close.

Your name goes with it

The Author field on your mod (Project → The mod's own details, or the Details… button at the top of the window) is written into the file the game reads, and the studio shows it beside your mod's assets. It prevents nothing. It does mean a piece of your work that turns up somewhere else has a name attached to it, and that somebody copying it has to actively remove that name rather than simply not think about it.

How it knows which mods are yours

Two things, and either is enough:

  • You installed it from here. Every install is recorded, in your own settings rather than inside the mod — a marker written into a mod folder would travel with a copy of that folder and claim to be everyone's.
  • You have the project file. Any mod in your mods folder counts as yours, which covers one you built on another machine and brought across.
If your own mod comes up locked

That means this installation has neither record: no install and no project file. Open the project and install it again and it is yours from then on.

Which is the real reason to keep your project files. They are small, they are the only editable version of your mod, and a build output cannot be turned back into one.

12Overrides: changing the game's own assets

An override ships a changed copy of one of the game's assets under its own name. This is how you unlock a hero specialisation, open up a weapon, or rename something the game already has.

Right-click the part in its section and choose Edit — not Duplicate. The sheet opens on the game’s own part, headed EDITING THE GAME’S OWN, and what you change is recorded as an override. A mod has to be open first. For an asset that no section lists, find it in the Data Explorer and double-click it: its fields open as a grid you can edit (Editing a game asset’s properties directly), and each change there is an override too. The bar along the bottom of the sheet counts your changes: Save changes writes them and Undo all of it drops them. The Studio edits both for you — but it is why an override that “looks right” can still do nothing, and why the build's own comparison is worth reading.

13Changing the numbers: balance mods

Damage, range, critical chance, overwatch arc, reaction damage — every number on every weapon lives in a plain data table that the game reads while it is running. No Unreal, no Blueprint graph, no bytecode. A balance mod is a handful of edited numbers in a table, and in this Studio they are boxes on a duplicated weapon.

Getting there

Open the Weapons section, right-click a weapon and choose Duplicate. The copy opens in its own tab. Find the NUMBERS card (“damage, rate, range”). Until you press Give it numbers of its own, a duplicate shares its kind’s table with every other weapon of that kind, the game’s included, and the card says so. Pressing it gives your copy a table of its own, and every number the weapon has becomes a labelled box.

Type a new value into a box. The change goes through the build’s own writer, and the Log says what was written or why it refused. A row you have changed is marked.

What the game actually reads

It reads the table. This is worth stating plainly because it is the one thing that makes the whole feature possible, and it was established the only way it could be — by shipping a mod and looking. Set a repeater's base damage to 88 and the armoury shows 90, the extra two coming from an attachment fitted to that weapon. Your number goes in at the bottom and the game's own modifiers stack on top, which is exactly what you want: the number you type is the number the game starts from.

One table can belong to several weapons

A table is named for a weapon type, not for a character. Attributes_RangedWeap_BlasterPistol_Default is the standard-issue pistol for everyone who carries one; Rex's DC-17 has its own. Before you change a number, read what the card says about the table you are on — shared with every weapon of its kind, or your own — because “buff the pistol” and “buff my pistol” are different tables.

Renaming, and saying what you changed

A rebalanced weapon that still calls itself by the stock name and describes itself with the stock text is only half a mod. Both are on the NAME card of the weapon’s tab, as Name and Description, and both work in game.

They are worth a note, because what you are editing is not what you might expect. A display name is not a string stored on the part — it is a reference to an entry in a shared string table, which is then looked up again in the game's translation file. Two indirections away from the asset anybody would think to edit. The Studio sidesteps both by replacing the whole thing with a literal, so your text is shown as written and no translation can override it. You do not have to do anything about that; it is just why the name in the file and the name on screen are not obviously the same thing.

The markup works

Descriptions accept the game's own rich text. <Bold>Base Damage</> comes out bold, and <Keyword id="UI.Keyword.ActionPoint">AP</> comes out as a keyword link, exactly as on a weapon the game shipped. ASCII only.

Abilities

A weapon’s abilities — its standard shot, its overwatch, whatever else it can do — are abilities like any other. Find them in the Abilities section (Changing what an ability does) to see what they are before deciding whether they are the thing you actually want to change.

14Changing what an ability does

Firestorm's damage, how long Disoriented lasts, how much accuracy it takes off you — all of it is data, and none of it needs the game unpacking. Open the Abilities section.

Find the ability and open it; the page shows where it lives and what it does. Then right-click it and choose Edit (a mod has to be open). The sheet that opens has a card for each place a number can live: PROGRESSION, every tier of the ability and what each costs; NUMBERS, the magnitudes in the ability itself (blast radius, throw range, the roster level it unlocks at); WHAT IT POINTS AT, the other assets that do its work; and TAG CONTAINERS, the gates. A card appears only when the ability has something to put in it. Most of the magnitudes live in the effects an ability applies, and the page says so; each effect opens as its own page, with the same cards. On NUMBERS every row is a box with what the game ships beside it, and anything you leave alone is not shipped.

An ability is a signpost, not a number

A GA_ asset holds almost nothing. What it holds is a list of the effects it applies — GE_ assets — and each of those carries the actual magnitudes. Firestorm applies five. That is why the page names the effects an ability applies, and why you will end up opening them: what a person means by “Firestorm” is all of it, and hunting through five assets for one number is what used to send people to a command-line unpacker.

Three reasons a number will not do what you expect

These are the whole reason the page is worth reading rather than skipping to the boxes. The Studio marks each one on the row, so you never have to find out by shipping.

What you seeWhat it means
read elsewhere — a curve tableThe number in the asset is a fallback nobody reads; the real value is a row in a curve table. Changing it builds cleanly and does nothing in game.
read elsewhere — worked out another wayThe magnitude is derived from one of your attributes, handed in while the game runs, or computed by code. Same story: the number is there, it is editable, and it is ignored.
not in fileNot a warning — an opportunity. The asset leaves this at its default, so the cooked file has no copy of it. Type a value and the Studio adds the property; the build reads the result back to prove it took. See below.

Most damage in this game falls into the first two. That is not the Studio giving up — it is what the game's own files say, and knowing it before you spend an evening on a number is the point.

This is a replacement, not a copy

Everything here is an override. You are shipping the game's own ability with a different number in it, so every character who has that ability is affected, and nothing new appears in any menu. There is no way to give one squad member a stronger Firestorm this way — that would be a new ability, granted by a specialization of your own (Making a specialization). What you can do is hand an existing ability, an enemy’s included, to a whole class by adding it to the class’s Abilities array: Editing a game asset’s properties directly walks through it.

Numbers the file does not carry

A cooked asset stores only what differs from its class default, so reading one tells you nothing about the rest of it. That is why GE_Cooldown_RocketStrike looks empty: it holds a tag and nothing else. Its class declares UsesPerCooldown as its very first property — the asset simply leaves it alone.

Rows like that are marked not in file and the box works. Type a value and the property is added.

Uses per combat, which the game already does this way

An ability that is “once per encounter” is not limited by a number — it applies a cooldown tag that lasts the rest of the fight. What decides how many uses you get first is UsesPerCooldown on the cooldown effect, and 18 of the game's 69 cooldown effects set it: GE_Cooldown_Medkit_T2 carries 2 and GE_Cooldown_Medkit_T3 carries 3. That is how the game tiers a medkit, and it is now how you can tier anything else.

Open the cooldown effect the ability applies (the ability’s page names it, and it opens as its own page), choose Edit, and give the row times it can be used before the cooldown applies a value. Setting it back to 0 removes the change, because a zero is not something the file format can store.

What is worth changing

Durations and stack counts are the reliable ones: how many turns a debuff lasts, how many stacks an ability applies, how much a flat modifier adds or takes away. GE_Disoriented takes 4 off accuracy and the box says so; type 25 and it takes 25.

A number that counts things — a stack count, the uses per cooldown, a roster level — is a whole number. Type a fraction into one of those boxes and leave it, and the box goes back with the reason in red above the list (“this number is a whole number”), rather than the build refusing it later. A box you tab through without typing records nothing, however many decimals the game’s own value has.

Above them sit the ability's own numbers, which are usually the plainest thing on the page: GrenadeBlastRadius, MaxThrowRange, BlastBaseDamage, OverwatchShotCount, and MinRosterLevel — which decides how far up the focus tree a tier sits.

15Tables: every other number in the game

What an action costs in action points, how long a duel runs, what a hologram tints to — most of the game's numbers are not attached to a weapon or an ability at all. They live in data tables: 853 of them in the game as it ships today, each a list of named rows with numbered fields.

The Tables section. Find one, and the page shows what kind of rows it holds, how many there are, which of its fields are numbers a mod can change, and the rows themselves. A table built from other tables lists them under Built from.

Changing a number

Right-click the table and choose Edit. A mod has to be open, because the change has to be written down somewhere. The page gets a NUMBERS card with one box for every number a mod can change, each labelled with its row and its field — BitReactor.AbilityCost.APx2 · ActionPointCost — and the game’s own value to the right of the box. Type a new value and leave the box. The row turns green, a Reset button appears beside it, and the card’s heading counts how many numbers this mod changes.

It is a list rather than a grid, on purpose: a table can have hundreds of numbers, and a box with its name beside it stays readable where a wall of columns does not. The find box at the top of the card narrows the list to the rows and fields whose name contains what you type. Type APx2 to see every number of that one row, or MovementAPCost to see that one number on every row. (It matches names, so a short word matches every name that contains it: ActionPointCost finds SpecialActionPointCost as well.)

What the box does

Nothing waits to be saved. A number is written into your project the moment you leave its box, so there is nothing to press afterwards. Typing the game’s own value back, or pressing Reset, takes the change out rather than recording “2 becomes 2”. A field that holds whole numbers rounds what you type to the nearest whole number, and the card says so when it does. Type a decimal with a point, 2.5; a single comma is read as a point too, so 2,5 means the same, on any PC. A number the box cannot use is refused with the reason in red above the list, and the box goes back to what it held.

Only numbers get a box. A true/false switch, a name or a tag has none; the Fields list on the table’s page marks the fields a mod can change, which are the decimal and whole-number ones. A field of any other kind, a byte or a 64-bit integer for example, has no mark and no box.

“zero, not stored”

A cooked table keeps no bytes for a zero, so a number that reads 0 may have nothing in the file to write over. It still takes a value: the build rebuilds that row to hold one. That is a larger edit than changing a number that is already there, and the box is marked so you know which kind you are making.

A project from an earlier version that already changes a table opens with those changes showing in the card, and builds the same package. The build log lists each one as row.field: 2 -> 4.

The build checks each change as it places it. The row and the field have to be in the table, the number there has to be the one the game ships, and the number it writes has to read back out of the rebuilt table. If any of those fails, the build stops with the row and the field named and installs nothing: it does not go looking for the old number somewhere else in the table, which could change a different one. That is what happens to a change that was made before a game update renamed or removed its row. (For table numbers the build does not read the finished package a second time; it is the placing of each change that is checked.)

In our own tests a changed number came back out of the built package as typed, with every other number in the table identical. What none of this can say is whether the running game takes a given table’s numbers from that file — which is the trap two boxes down, and the reason to test a table edit by playing it.

A row is shared by everything that names it

“Make Precision Shot cost less Advantage” comes down to one row, BitReactor.AbilityCost.GeneralADVx6 — and that row is named by every ability costing six Advantage. Changing it would be the right edit and it would not be one ability; it would be a balance change several times the size of the one you meant.

Some tables are built from other tables

DT_Costs is a composite: it declares that its rows come from DT_CostsTable_v4. Cooking baked a copy of those rows into both, so five tables in that one folder all look alike, and the running game may only take its numbers from one of them.

The page says so: it is headed composite, lists the parents under Built from, and the NUMBERS card says it again. If a change to a table ever builds, installs and does nothing in game, that is the first thing to check — the same change may be needed in the parent table too.

What this is not

A change to one of the game’s tables, however it is made, is an override — you are shipping the game’s own table with different numbers in it, so it applies to everyone and everything that reads it. If you want a duplicated weapon to have damage numbers of its own without touching every other weapon of that type, that is a different thing: duplicate the weapon and press Give it numbers of its own, which copies the table for you.

16Making a specialization

A specialization is the class a recruit is — Assault, Scout, Padawan. It is a part in exactly the sense everything else here is a part, and it has no mesh whatsoever. What it has instead is a name, an icon, a few abilities granted outright, a starting gear kit, and a focus tree: three lines of ability tiers, seventeen rungs in all, which is what a player spends focus climbing.

Making one is the same loop as everything else. Open the Specs tab, find the specialization closest to what you want, and right-click it and choose Duplicate. All of it comes across — every ability, every rung, the gear kit — and you change the parts you want different. It arrives in whichever mod you have open, and the Studio takes you straight to it.

Copy the closest one, not the simplest one

Your copy inherits everything you do not change, so the template is doing most of the work. Start from the specialization whose tree shape and theme are nearest your idea, not from whichever one you happen to know best. A Force-flavoured class built on Padawan needs three edits; the same thing built on Assault needs seventeen.

What it will not do, and tells you so

Some things are fixed by the specialization you copied, and the build reports each one rather than quietly ignoring it:

  • Taking a granted ability away, and adding or removing a gear kit. The card has Remove and Grant a gear kit…, but those lists are a fixed length in the file. The build says this mod lists N … and its template has M — one cannot be added or removed and compares only the entries both have. You can change which gear kit it is; you cannot add or remove one.
  • The shape of the tree. Three lines, with as many rungs as the template has. A rung can be given a different ability and different numbers; rungs cannot be added or removed. A number the game ships as 0 cannot be raised: it takes no space in the file, so there is nothing to write over, and the build says so if you try.
More granted abilities than the template had

This one works. Press Grant an ability… past the number the template grants and the Studio appends the extra abilities after the template’s own. A specialization granting more abilities than the one it was copied from has been confirmed in a mission.

Choosing an ability

Press Change… beside any granted ability or rung and a searchable list of every ability in the game opens, with the family each belongs to shown beside it. Choose one with Use this one and the Studio writes the reference correctly.

This is why it is a list and not a text box

An ability reference is a full path, and the folder in it is not the one anybody would guess. GA_Firestorm lives under Gunslinger and GA_BullRush under Soldier — while the Assault specialization grants both of them. Typing these out from memory gets them wrong.

Tiers have to match, and that part is on you

A line of the focus tree is a ladder of the same ability getting stronger: GA_Firestorm_T1 through T6. Replace all six with the six tiers of something else and it works. Replace one rung of six with a single-tier ability — most hero abilities are single-tier — and the remaining five rungs still grant the old one. Nothing is broken; it simply is not what you meant.

Rex and Anakin cannot be duplicated into a usable class

Their kits have no focus tree at all — zero lines, zero rungs. The picker draws a three-line tree and will not offer a specialization that cannot fill one, so a copy of a hero kit never appears however open you make its tags. Three separate attempts went into removing gates before that was measured. The Specs tab shows the rung count for exactly this reason: if it says zero, stop.

What does work is the other direction — put a hero's abilities into a copy of a real class. That is how “Jedi Knight” got made: Padawan's tree carrying Anakin's four abilities.

A hero's class is unlocked for you

Hero specializations carry their owner's name tag, and a plain copy would inherit it — giving you a brand-new class that only Tel-Rea can choose. Duplicating drops that tag, from both the asset and the record the menu actually filters on. Leaving Only for blank is all you have to do.

Why the identity tag stays the same

A duplicate keeps its template's identity tag, which looks like a mistake and is not. A specialization sharing that tag has been built, shipped and played: it appeared in the picker and the game's own recruit generator started rolling it onto new recruits. A freshly invented tag is one the game's tag table does not define, and nothing outside Unreal can register it — so it may simply resolve to nothing. The Identity box on the WHO CAN TAKE IT card is yours to change if you want to try; it is not changed for you because the default is the thing that is known to work.

There is no picker list to add yourself to

The game finds specializations by their slot tag in the asset record, not from a list of the eight it ships. Build one correctly and it is offered — and the recruit generator treats it as a first-class member of its own pool, which means recruits will turn up already wearing your class. Whether that is what you wanted is a design decision; it is not something that can currently be separated.

17Making a weapon

A weapon is not one asset. The Armoury lists a part; that names a gear kit, which names the weapon actor, which names the loadout, which names a type part carrying the weapon’s tag — and that tag is what picks the weapon’s meshes out of palettes shared by every weapon in the game. Five files and five mesh palettes, and on disk nothing says they belong together. The Weapons tab shows a weapon as one weapon, and does the copying for you.

Open the tab, pick the weapon closest to what you want, and right-click it and choose Duplicate. Every link is copied under your mod’s name and re-pointed at the others, and the copy is routed onto a weapon class of its own. It arrives in whichever mod you have open. Nothing of the game’s is written over: the weapon you copied keeps every part it has, and yours stands beside it.

It gets its own shelf

A duplicate is not squeezed in beside the game’s own weapons of that class. It goes onto a Custom Longarm, Custom Rifle, Custom Pistol or Custom Repeater shelf, defined by a small mod called Custom Weapon Classes that this tool ships and installs for you the first time you need it. You can also give a weapon a shelf of its own, with a name you choose — “Bob’s Heavies” sits in the class list like any of the game’s. On the SHELF card that is a name, a behaves like choice and Make a shelf of my own; the other buttons there move the weapon between the custom shelf and the game’s.

It also keeps your weapons out of the game’s own lists, which is tidier for anyone who installs your mod: their Longarm shelf still holds the four the game shipped.

A long list sometimes draws a blank row, and it is not your mod

Once a weapon class holds eight or so, the Armoury will occasionally draw one row with no name and no picture. It is still selectable, and it still works. Scroll, or leave the screen and come back, and it will be a different row — or none.

That is the game’s own list reusing its row widgets: a row fades itself in with an animation, and one that gets reused without replaying it stays invisible. It happens on the game’s own weapon classes too, with no mods installed past the count. Nothing in your mod causes it and nothing in your mod can fix it — the tool says so at build time rather than letting you hunt for a fault that is not yours.

If you model the whole gun as one piece

If you do want them all, it is four more meshes per slot, each positioned for your gun.

The scale on your FBX is not always right

If a piece comes out wildly wrong the build refuses the import, ships the game’s mesh instead of yours, and says what the file claims and what the game measures. Read that line: it names the number to set as the mesh’s meshScale in the project file. The HOW IT FITS card, with its cm per unit box, is offered for a part but not for a weapon’s pieces.

What it also offers — “a scale of 188.313 would match its height exactly” — is right for one mesh replacing one mesh and wrong for a set. Taking that number for each piece of a split gun scales four pieces by four different amounts and pulls the model apart. For a set, one scale for all of them, and check the centres.

18What attachments do: changing a modification

The barrels, cells, scopes and stabilizers a player buys in the Black Market and fits in the Armoury. There are 64 of them — four styles per slot, four tiers per style — and what each one does is a single number on its ability asset.

This is a different thing from the attachment list on a weapon you duplicated. That one decides which piece appears on the gun when a modification is fitted. This one decides the +2 Critical Hit Damage.

The Attachments section

The Attachments tab lists all 64, under their slot and style: Barrels · Condenser, then the four tiers of it in order, with the number each one carries at the right of its row. The filter box finds a modification by its name, by its family (Phase Adjuster) or by what it says it does (Critical Hit). Click a row to read it: what it does, its number, what it costs, how rare it is, and the four tiers of its style side by side, so a number can be judged against its neighbours.

A row this mod changes wears the accent colour and a bar, as in every other section.

Changing one

Right-click the modification and choose Edit. A mod has to be open, because the change has to be written down somewhere. The page gets two cards, one for each of the two assets a modification is made of:

What the boxes do

Nothing waits to be saved. A change is written into your project the moment you leave its box, so there is nothing to press afterwards. Typing the game’s own value back, or pressing Reset, takes the change out rather than recording “2 becomes 2”. A number the box cannot use is refused with the reason in red above it, and the box goes back to what it held. Type a decimal with a point, 2.5. A single comma, 2,5, is read as a point too, on any PC; but a comma followed by exactly three digits, such as 1,500, could mean 1500 or 1.5, so it is refused with both readings named and you type it again without the comma.

A price is a whole number of credits and cannot be negative: a fraction is rounded and a negative becomes 0, and the card says so when it does. Rarity is one of the four the game ships, Common, Uncommon, Rare and Unique, one to a tier.

A percentage is typed as a percentage

The Rapid Cycler’s chance to restore an action point is stored as 0.06 and a player is shown “6%”. A box showing 0.06 would invite you to type 15 for fifteen percent and ship a 1500% chance, so these are shown and typed as percentages: the box reads 6, the game’s own column reads 6%, and the card says so under the label. Which modifications are percentages is read from the game’s own data, not guessed from the size of the number.

{effectDescription_1} in what it says

Every modification’s sentence holds {effectDescription_1} where the number goes. The game fills that in with the number when it shows the sentence — the “6%” of the Rapid Cycler appears at run time, it is not written in the text. Keep {effectDescription_1} wherever the number should appear in a sentence you write: take it out and the sentence stops saying the number.

The four that carry no number

Balancing T2 and T3 and Ergonomic T2 and T3 do not carry the main number at all: they use the tier below’s and raise only their cap, and a cooked file does not write a value that has not changed. They get no box. The row says inherited and what the tier below is using, and has a Give it one button. Pressing it adds the property rather than writing over one, which is a larger edit than the rest, starting at the value the tier was using; after that the box and the Reset button are there like any other. Their caps are ordinary boxes: the caps are the only difference between some of these tiers.

A modification is two assets

What it does lives on an ability; what it is called, how rare it is and what it costs live on a separate shop item, joined to the ability by name. The two cards are those two assets, and a mod can change either without the other. Both are ordinary overrides, so they ship, verify, clash and uninstall like everything else.

One asset, every weapon

A modification is a single asset that every gun in the game reads. Change the Single Coil Condenser and it is changed for your weapons and for the game’s alike, on every save. That is usually the point of a balance mod; it is worth knowing before you halve something.

It also means two mods that edit the same modification collide, and the build’s clash check says so at install time.

Two numbers the game keeps that disagree

Most tiers keep a second copy of their number, the one the menus hold. It moves with the number where the two agree in the game’s files. Four modifications — the top three tiers of the Tracking Scope, and the IQ Ergonomic stabilizer — disagree with themselves in the game’s own data (the IQ Ergonomic does 2 and its copy says 3): the card says so in amber and leaves the copy as the game shipped it, because nothing here knows what the copy is for.

The build proves the number, and you should read the line

The build log says “2 → 12, reads back 12 as a double at byte 1980”, and then again after the container is mounted: “its numbers read back: GameplayEffectModifer = 12”. A name, a sentence, a rarity and a price are read back the same way (the name it reads back, the tags in ItemTags, BuyCost = 2500). Each is the asset being read, not the tool repeating its own intention — a stat is stored as an eight-byte number whose upper half looks exactly like a four-byte one, and an earlier version of this wrote into the middle of it, reported success, and produced 134,217,728.

A project from the earlier Studio that changes attachments opens with those changes showing on the cards and builds the same package. In our own test, a project written by hand in that format built to the same package, byte for byte, as the one this screen wrote for the same changes; the pak differed only in the description and author the hand-written project carried. Proof so far is the built package read back, a number, a name, a sentence, a rarity and a price at a time; a changed modification has not been written up as seen in a play session.

What it will not do

  • Make a 65th. Duplicate is greyed out in the right-click menu here. The 64 are changed in place and nothing uses a modification up; whether a mod can add one the Black Market will sell is not settled, so it is not built.
  • Change its picture. The icon on the shop item is not on these cards.

19Making a recruit out of an enemy

The game fights you with battle droids and never lets you have one. You can hand one to the player: a B1, a B2 or a BX commando who joins the company, carries his own weapon, moves in his own animations and takes his turn like anyone else. None of it needs anything running beside the game, and none of it touches an asset the game ships.

Start on the Recruits tab. It lists the roster the game hires from. Right-click a row and choose Add somebody to this pool… — the picker offers every character the game has, so a B2 or a Magnaguard who is in no pool at all is there too — or choose Duplicate on a row that already names the enemy you want. The Studio copies what he is made of into your mod, leaves him the name the game gives him (you change it on his page), and opens that page. Everything after that is the boxes on that page.

Take their place… does the same job from the other end: it points the row you right-clicked at him, so the recruit who was in it stops being offered. It is the one that costs somebody, which is why Add somebody to this pool… comes first; Put this row back undoes it.

The boxes, and what each one is really for

BoxWhat it does
Spawn on a pawn of the mod's ownShips a copy of the enemy's own pawn and points your character at it. Without this he is built on a hero's body and stands like a human. Leave this on.
Also ship a weapon for the ArmouryA blaster in the Armoury that carries this droid's animation tables and his stance clips. Equip it on him and he aims, turns and fires as himself.
List only their own gun in itWithout this, that blaster is a copy of the rifle class and lists every rifle in the game. With it, the class holds one weapon: the gun the droid's own kit carries, made equippable, with the shot animation and the tags his cinematics ask for.
Also carry that tactical spec in a spare slot (experimental)This is what gives him action points. An enemy's move and turn basics ride on his tactical specialization, and the hiring pool throws that away. A spare slot is one the hiring pool never touches, and a part still applies from there.

The four boxes that work

Pawn, weapon, only their own gun, and the tactical spec in a spare slot. That combination is confirmed in a real campaign: action points, his own animations, his own gun, and the Armoury offering that gun to him and to nobody else. Add a box beyond those four only to see what it does.

Separatists do not appear on the mission-ready screen

Your droid plays normally and shows up everywhere else, but the squad-select screen before a mission draws him as nothing at all. That screen does not show your characters the way the battlefield does: it renders a hologram, and the hologram is one fixed actor with a human body, with each character's customization applied on top of it. A droid's body is not in his customization — it is on his own pawn, on a skeleton that actor cannot wear — so there is nothing for it to draw.

It is cosmetic. He deploys, he fights, and he is on the field when the mission starts. Nothing in a mod reaches that screen, because the proxy it uses is a single asset the game picks by itself.

Joining without being hired

There is a second route, and it is unfinished. A campaign recipe can add a character outright, the way the story adds one, and a character who arrives that way never goes through the hiring pool and never has his class or weapon rolled away. The Studio can build it — a pawn class of your own, a copy of a story recruit recipe, and the recipe written into every chapter's arc — but no campaign has been played through on a sound build to confirm it, so it is off by default and marked UNTESTED in red on the character’s page: it is the Join by story recipe box on the HOW THEY PLAY card. Turn it on there if you want to try it, and expect to end a cycle in chapters two to six before anyone joins.

20Editing a game asset’s properties directly

Every section so far is a guided view over some of the game’s assets. This is the other route, and it reaches all of them. The Data Explorer (Home Page) lists every file in the game; double-click an asset and its fields open in a grid headed Properties. Change a value there and it is recorded in your mod as an override of that one asset — the same mechanism as section 12, with a box instead of a card. The 3D viewport has a Properties side tab that is the same grid.

A mod has to be open before you can change anything. Without one the Log says open a mod first — an edit has to be recorded somewhere.

Reading an asset

A cooked file stores only what differs from its class’s default, so a property you cannot find in a file may simply be absent. The grid lists every property the class declares, and writes (default) in the value column for the ones the file says nothing about. That is not “empty”; it is “the game’s own default”.

  • Order. The asset’s own class first, then up the chain of classes it inherits from. A faint class name beside a property marks one that was inherited, and from where. Unreal’s editor groups properties by category; the categories did not survive cooking, so there are none here.
  • Names and types. The name is the one Unreal’s editor shows (“Slot Can Be Empty”); hover it for the raw identifier. The faint word after it is the type, spelled the way Unreal spells it: FGameplayTagContainer, TArray<TSoftObjectPtr>. The Filter box matches the display name, the raw identifier or the value.
  • The footer says which package you are looking at and which container it was read from — with a mod installed there are two copies of one package, and it is worth knowing which this is — and ends N properties · M at default.

Changing a value

Double-click the value, or right-click the row and choose Edit value. Enter commits and Escape cancels. A row your mod has changed is drawn in the accent colour, and the file is marked in the Data Explorer (Show only modified lists everything your mod changes).

Every edit is first rehearsed with the build’s own writer against the game’s own bytes, and is recorded only if the rehearsal agrees. A refusal says why in the Log, and the box stays open with what you typed still in it. It works at any depth, including properties inside a struct such as UIData.Name.

The row is…You get…
A numberA box. The number has to be stored in the file already; one left at its default has no bytes to write over.
True or falseA checkbox. A bool left at its default still shows its box, and the rehearsal decides: false to true often cannot be written, because the file stores nothing for a default.
One of a fixed set (an enum)A dropdown of its own members.
A nameA text box.
A stringA text box. The one edit that can make the file longer or shorter.
Text a player readsA text box. The edit replaces the lookup in the game’s string table with a literal, so it shows as typed and no translation can override it — the same thing the Name box does on a card.
Anything else (a struct, an object reference)No box of its own. Open it and edit the fields inside, or follow the arrow (below).

Revert on a row (right-click) puts back a number, a tick or a dropdown choice. Names, strings, text and array entries are put back by right-clicking the file itself in the Data Explorer and choosing Revert, which takes every change your mod makes to that file off it.

Confirmed in game

Editing text a player reads works: a changed name and description showed as typed on the Personnel page and on the action wheel.

The tick box, the dropdown and the name and string boxes have been read back out of the built file for each kind, but have not yet been seen in a play session.

Arrays

An array whose entries are soft references to other assets — a specialization’s Abilities, AbilitySets or GameplayEffects, say — gets a + on its row and a ✕ on each entry.

  • + opens a picker titled Add to and the property’s name. It offers the game’s assets with the name prefix the existing entries share (GA_ for abilities), so you choose among the game’s abilities rather than among every asset in the game. An empty array has no prefix to read, so it offers everything and says so.
  • ✕ takes that entry out.
  • The count beside the array is the file’s and stays the file’s. What your mod did to the array is written beside it in the accent colour, + GA_Name or − GA_Name, because the grid shows the game’s bytes and an entry you added is not in them. Without that stamp the button would look as if it did nothing.

An array of structs — a progression’s LeveledAbilities, say — gets a + that copies the last entry and a ✕ on each element. You then edit the copy field by field. The stamp reads + a copy of [n]. A struct entry cannot be made from nothing, only copied: its header says which of its fields are stored, and one written from nothing would be a guess.

The limits: an array of hard object references gets no button; an array cannot be emptied (the cooked file stores an empty array as no bytes), so its last entry stays; and two adds are two entries.

Adding to an array of soft references is confirmed in game (the worked example below). Copying and dropping struct entries has been read back from the built file — a three-entry progression became four, and another dropped to two — but not yet seen in a play session.

Following a reference

A row whose value names another asset shows an arrow, →. Click it and that asset opens in a tab of its own; hover for the target. It is how you get from a part to its fragment, from a specialization to its base Blueprint, from an array entry to the ability it names. A target that is not in the mounted game — one of your own mod’s assets, say — is named in the Log rather than silently doing nothing.

Worked example: give an enemy’s ability to your operators

A widespread belief is that the game does not allow enemy abilities on operators. It does. The ability only has to be in the class’s list.

  1. Find the class’s tactical spec With a mod open, type CPD_TacticalSpec_Assault into the Data Explorer’s Filter and double-click it. Any specialization’s CPD_TacticalSpec_ asset works the same way.
  2. Find its abilities In Properties, open CustomizationFragmentAbilities_0 and look for the Abilities row. Typing Abilities into the grid’s own Filter gets you there.
  3. Press + on the Abilities row In the Add to Abilities picker, choose a GA_ asset — an enemy’s will do.
  4. Build and install Every operator of that class has the ability, on the Personnel page and on the in-mission action wheel.
Confirmed in game

Two enemy abilities, Devour and Resonate, added to the Assault class this way showed on the Personnel page and on the action wheel.

A two-step ability needs both halves

Devour requires the Bind status that the Coil Seer puts on its target. Grant Bind beside it, or Devour is a button that never fires.

Enemy abilities take their words from a table the player UI does not load

The name draws red, as <MISSING STRING TABLE ENTRY>, until you give the ability literal text. Open the ability itself and edit its name and description as text a player reads (the table above), typing the words you want. That replaces the lookup with a literal and the red text goes; this part is confirmed in game too.

An ability is a snapshot in the save

Operators you already have keep the abilities they had; new recruits get the new ones.

The wheel has only so many places

The action wheel keeps only what fits — four places in a class row, six in the utility row — and sorts the lowest SortingPriority first, so a granted ability can be dropped from a full row. That rule was read from the game’s own scripts rather than tested to its limit.

The same route grants any existing ability to any class. A specialization of your own can be given more abilities with Grant an ability… (Making a specialization), and Changing what an ability does is for changing the numbers inside one.

21The Level Editor: moving, replacing and adding things in a map

The download holds a second program beside the Studio: ZeroCompanyLevelEditor.exe. It opens the game’s maps, draws them in 3D, and lets you move things in them, change what they draw, and add more. It opens the game read-only and never changes the game’s own files. What you do is saved into a mod project, and Build and install turns that into a mod in the game’s Mods folder, the same way the Studio’s Install does.

Before you start

  • Where the game is. The first time it runs it asks the Studio’s question, Where is Star Wars Zero Company?, unless the Studio has already been told. The answer is saved in the same settings folder, so whichever program is told first, the other already knows. Project → Find the game again… changes it for both. If the Level Editor already has a game open when you change it, the window tells you to close the program and open it again.
  • A mod to save into. The Level Editor opens a mod project; it does not make one. Create a mod in the Studio first (Project → Create New Mod), then in the Level Editor use Project → Open mod project… and pick its .json. Without one, saving and building say no mod project is open.

Finding your way around

The Maps list on the left holds the game’s maps. Click a map to open all of it, or open its arrow and click one sublevel to load just that piece, which is far quicker on a big map. The Actors tab lists what is in what you opened and the 3D viewport tab draws it. Click an actor, in the list or in the viewport, to select it; the panel on the right says what it is and where its position was read from. View → Show viewport statistics adds a block of rendering counters to the corner of the viewport; it is off every time the program starts.

What you can change

  • Move. Pick the Move tool and drag an arrow on the selected actor, or type numbers into Transform (location in centimetres, rotation in degrees, and scale). One drag is one undo step. Moving an actor is confirmed in game.
  • Replace what it draws. In the actor’s Draws section pick another mesh from the list. The list offers only meshes that sublevel already uses. Remove it makes the actor draw nothing; the actor stays in the level. Changing what an actor draws is confirmed in game.
  • Add. The asset list on the right offers This level or Whole game. Pick an asset and the panel says whether it can be placed; when it can, a new actor is put where the 3D viewport is looking, and you drag it with the gizmo. Place another at the camera puts down more. A new actor is always a copy of one the level already holds, so it takes that actor’s rotation and scale — only the three location numbers are written for a new one. Adding an actor and building it into the game is confirmed in game.
  • Rotate and scale are built, and the build writes them, but nobody has launched the game and looked at one yet. Treat them as untested.

Some actors cannot be moved at all, and a few things cannot be done in this program. The Limits tab says which, and why.

Saving, building and installing

Your changes pile up in the Changes tab at the bottom. Project → Save changes to project writes them into the mod project, merged into what is already there. Edit → Revert all changes throws away your pending moves and mesh changes as one undo step.

Project → Build and install saves, builds, reads the result back, and installs it, stopping at the first thing that refuses. It opens the Log tab so you can see why. If the read-back finds a problem, nothing is installed. The mod goes into the game’s Mods folder like any mod from the Studio. Close the game first: if one of the mod’s files is in use, it says so and installs nothing.

Taking the level out as a file

Project → Export what’s loaded to FBX… writes what the 3D viewport is drawing right now as one .fbx file, with the textures beside it, so you can open the level in a 3D program. It asks for a folder and makes a new folder inside it named after the map or sublevel you have open; if that name is taken it adds _2, _3 and so on, so nothing you already have is written over. The entry is greyed out until a map or sublevel is open, and while one is still being read.

  • It matches the screen. The file holds the placements the viewport is drawing. A sublevel you have unticked, the backdrop when you have switched it off, and the greybox when it is hidden are left out. The greybox is hidden until you press Blockout, so a map with a lot of it exports far less than it holds until you do.
  • Wait for the viewport to finish loading. The viewport loads a map’s meshes only while the 3D viewport tab is showing, so if you choose the entry from another tab it switches to the viewport and asks you to try again. A placement whose mesh is still loading, or would not load, is not in the file, and the Log says how many were left out and why.
  • It is the game’s own map. Every placement is where the game puts it and draws the mesh the game gives it. Your own changes — moves, mesh changes, removals and new actors, whether they are saved in a project or not — are not in the file; a placement you have removed or swapped is in it as the game has it.
  • What the file looks like. There is one empty group for each sublevel, named after it, and under it one object for each placement, named after its actor (a repeated name gets _2, _3). A mesh that is used many times is stored once and shared by all its placements, which keeps a map with thousands of placements small. A skeletal mesh is written in its reference pose as plain geometry.
  • Textures. Each material’s base colour and normal map are connected to its material in the file. A material the viewport draws as a cut-out (leaves, grass cards, decals: the game’s blend mode is Masked or Translucent, or it uses the base colour’s alpha) also has that texture’s alpha connected as its opacity, so the cut-out shows in the other program. In 3ds Max the cut-outs need one more step: when the level has at least one cut-out material, a .3dsmax-cutouts.ms file is written beside the export (a level with none gets no script), and you run it once after importing (Scripting → Run Script; it is written for 3ds Max 2017 and newer and was tested in 3ds Max 2027). As measured in 3ds Max 2027, Max’s FBX importer reads the opacity texture as a Physical Material’s Transparency map, whose weight is 0, so the leaves arrive solid; the script gives each listed material a Cutout map that reads the base colour image’s alpha, which an import cannot do. Every texture is written as the game ships it, alpha included. The base colour of an opaque material whose texture has any alpha that is not fully opaque is connected to a second copy without the alpha channel instead (its name ends __rgb), so a texture that keeps something else in its alpha never turns a solid surface see-through; the cut-out materials are connected to the file with its alpha. Normal maps are written as the game ships them, DirectX-style (green channel down), which is 3ds Max’s own convention; Blender expects green up, so in Blender invert the green channel alone between the image and the Normal Map node: a Separate Color node, a Math node set to Subtract (1 minus green), and a Combine Color node. (An Invert Color node inverts all three channels and breaks the map.) The manifest says, for each material, its blend mode and whether it is a cut-out. Every other texture a material uses is written too, into the Textures folder next to the file, once each, named after the texture. The file <name>.materials.json beside it lists, for every material, the file each of the game’s texture parameters became and the numbers the material sets (tint colours, strengths and switches).
  • Progress, cancel and the summary. A progress line with a Cancel button shows above the status bar while it runs, and the window stays usable. Cancel removes everything the export has written so far, and so does closing the window while it runs (the window closes once the removal is done). When it is done, the Log tab gives the counts and the time, and says what the file does not hold. What the viewport left out (an unticked sublevel, the backdrop, hidden greybox, meshes still loading or that would not load) is given as a number for each reason, with the first few meshes that would not load named. What the export itself could not write, such as a texture with no pixels in the game’s files (a render target, for one), is listed by name with the reason, the first forty of them; the .materials.json file names every one, so if the Log says there are more, that file has the rest.

Two commands that open no window

ZeroCompanyLevelEditor.exe --version prints Zero Company Level Editor 2.0.0 and exits. ZeroCompanyLevelEditor.exe --check does what the program does at start — it finds the game the Studio’s way, checks the mappings against the installed build, opens the game read-only and counts the maps — and says what happened. The exit code tells you: 0 means the Level Editor would open on your game, 3 means it would have to ask where the game is (start the Level Editor or the Studio once, then run it again), and 1 means it cannot be set up.

Updates

The Level Editor never looks for a newer version by itself, and its About window has no switch for it. The Studio does. In both, About → Downloads and updates opens the releases page in your browser and does nothing else.

22The project file: things that have no button yet

A mod is one .json file in your mods folder (Documents\Zero Company Mods, unless you moved it), and the Studio writes it for you. It is plain text, comments and fields the tool does not know survive a save, and a handful of things are reachable only by editing it. Those are collected here, each with how far it has been proven. Where something is not proven, it says so.

Unload the mod before you edit its file

The Studio keeps the project in memory and writes it back whenever it saves, so a hand edit made while the mod is open can be written over. Use Project → Unload existing mod, edit the file, then open the mod again.

slotSets: add slots to parts, including colour slots

A slot is a place on a part where something else can be fitted. slotSets is a list of sets, each stamped onto every one of its targets when the mod is built:

"slotSets": [
  {
    "id": "SideAttachments",
    "targets": ["MyAttachmentsCategory"],
    "slots": [
      { "id": "Side",
        "tag": "br.Customization.Slot.Character.Outfit.Helmet.Attachment.Rangefinder",
        "name": "SIDE ATTACHMENT",
        "fits": ["br.Customization.Accepts.Attachment.Clo002"],
        "canBeEmpty": true,
        "camera": "br.Camera.Hub.Customization.Head" },
      { "id": "SideColour",
        "tag": "br.Customization.Slot.Character.Outfit.Helmet.Attachment.Rangefinder.Color.Primary",
        "name": "SIDE COLOUR",
        "fits": ["br.Customization.Accepts.Outfit.Color"],
        "default": "/Game/Game/Customizations/Characters/Humanoid/Outfit/Color/CPD_H_Outfit_Color_None",
        "canBeEmpty": false,
        "paints": { "slot": "br.Customization.Slot.Character.Outfit.Helmet.Attachment.Rangefinder",
                    "materialSlots": ["MI_HELM"], "channel": "Color 01", "small": true } }
    ]
  }
]
  • targets is a game part’s package path (the build overrides that part) or the id of one of this mod’s own parts or copies — here, a copy called MyAttachmentsCategory. An id that belongs to both a part and a copy is refused by name rather than guessed at.
  • Each slot’s id is yours, used in reports and never written to the game. tag is the slot’s own tag, name is the label a player reads, fits is the tags of the parts it accepts, canBeEmpty and camera do what they say. icon and default are object paths to a game texture and a game part; default may instead be the id of one of this mod’s own parts or copies. A slot whose tag the part already carries is a duplicate and is refused.
  • paints makes a colour slot: slot is the slot it tints, materialSlots names which of the mesh’s material slots (by name), channel is Color 01 to Color 04, and small gives it the small-tile look.
  • Every tag a slot set uses is registered in the mod’s own tag config for you; none needs listing twice. A key the build does not know, or a known one of the wrong type, is refused by name rather than dropped.
Confirmed in game

Slots written this way load in game, with their names, and colour slots appear as tabs (2026-09-24). An ATTACHMENTS category on the Outfit wheel built from them has been seen too: on 2026-10-11 with its Outfit file placed in ~mods by hand, and on 2026-10-31 built and installed by the Studio alone.

Not proven yet

A part appearing in the new slots has not been seen: the placeholder part used in testing carried helmet tags, so the slots offered only None. A colour slot actually tinting a model has not been seen. What happens to a character when a mod with these slots is removed is an open test.

Three things measured in game, each of which costs an evening

A slot lists only the parts that carry the slot’s own tag in their AllowedSlots; fits alone listed nothing but None. Give the part the tag with addTags, below.

A slot placed on a part the player picks kills that part’s picker: its button turns into a group and the helmet grid cannot be reached. So no per-helmet slots; put them on a container of your own.

Customization is a snapshot in the save, so a new slot reaches new characters only.

addTags: tags to add to a part or a copy

On a parts entry or a copies entry: a list of tags to add to the asset’s AllowedSlots and, if it has one, to its registry entry. The menu filters a part by its registry copy of its tags and offers it in a slot only when it carries that slot’s own tag, so giving a part the tag is what addTags is for.

  • On a part it is applied after the build strips every br.Customization.Accepts.* tag (which it always does, to drop the template’s own unlock gates), so what you add survives.
  • On a copy nothing is stripped, and it only adds beside the template’s tags. A copy whose template is not a registered primary asset has no registry half; that is not a failure.

It is not the same as Add tags on the TAGS card, which is the override tool for the game’s own parts. The read-back line is its added tags read back. Proof: read back from the built file, and the rule it exists for was measured in game (above). No part has yet been seen appearing in an attachment slot.

clearSlots: empty a copy’s own slot list

On a copies entry: "clearSlots": true empties the copy’s own list of slots and keeps its other fragments, in order. The slot objects stay in the package; they are only unlisted, so a tag asked for again on the same copy counts as a duplicate. It is what turns a copy of the Tops container into an empty container for a category of your own, and it runs after the copy’s rename and addTags and before any slotSets are stamped in. A template with no slots is refused by name. The read-back lines are its template’s slots are cleared and its template’s other fragments are kept.

Proof: the ATTACHMENTS page on the Outfit wheel made from it is confirmed in game (2026-10-11 with the early file placed by hand, and 2026-10-31 from the Studio alone).

Values the grid does not write

An override’s values list is a list of typed changes, { "row", "field", "kind", "was", "now" }. The Properties grid writes the kinds name, string, text, softadd, softremove, structdup and structdrop. Two more kinds have no button:

  • scriptconst changes one constant inside a Blueprint function’s code. row is the function, field is the constant’s type (double, float or int), and was and now are its old and new values. It is refused unless there is exactly one such constant in the function; the swap is the same size, and the function is decoded before and after and must differ by that one number. Confirmed in game: a menu’s radius changed from 50 to 250 and the menu drew at the new size. There is no editor for Blueprint code beyond this.
  • mapadd copies a map entry under a new key. row and field are the export and the map property, was is the entry to copy and now is the new key — a status effect’s words in a map of effect texts, say. List it before any value that names the new key, since values apply in order. Confirmed in game: a new status name showed on screen with the right words.

A path may name a map entry by its key: Fail Text Map[Ability.ActivateFail.TagsMissing].

An ability copy’s own words

The tab of a copy of a GA_ ability has Name, Description and Long description boxes on its NAME card; the last reads Empty keeps the game’s own text. An empty box gives the text back to the game: the entry is removed, not written blank. The tab and the mod list show the ability’s Name instead of its id.

The catch is that nothing in the Studio creates an ability copy. Duplicate on a row of the Abilities section says Duplicate is not built for Abilities yet. A copy exists only when the project’s copies list already holds an entry whose template is the package path of a GA_ ability, written by hand.

Proof: the text writers under the boxes were confirmed in game through two ability copies in a test mod — their place on the wheel, tooltip, status name and duration all came out as intended. The three boxes themselves have been built and tested, but not yet seen in a play session.

23Traps that cost real hours

  • Ids must be unique across installed mods. Not just within your mod. Two mods sharing an id cook to the same package path and one silently wins.
  • A helmet that does not hide the head renders the character's face and hair through the visor.
  • A mesh path without its .AssetName suffix imports as an empty pointer, and the part equips nothing at all.
  • “Restriction expected” does not restrict anything. It only tells the checker what you meant.
  • Edition and story gates travel with a copy. A development gate does not. If the build says your part is gated, it will not appear no matter how correct everything else is.
  • Close the game before installing. Every time.
  • A mod that changes one of the Outfit wheel’s own files has a second half in ~mods. Removing only the folder from Mods leaves that half overriding the game’s file; rebuild after every game patch; and unequip and save before you remove it. A mod with a second half.
  • Read the build log when something is odd. It reports what it changed, and the comparison names anything that changed which you did not ask for.

Weapons

  • A weapon model that already has a barrel needs the barrel slot emptied. Otherwise the weapon you copied lends you its own and you get two. This Studio has no button that empties a piece yet: Making a weapon.
  • A split model must come out of one scene. Each piece carries its own position — there is no offset field — so aligning them is done in your modelling tool and nowhere else.
  • Compare centres, not sizes. The build prints both. A piece of yours being a different size from the one it replaces is expected; a different centre is the misalignment.
  • “A scale of N would match its height exactly” is advice for one mesh, not for a set. Following it per-piece scales a split gun by a different number each time and pulls it apart.
  • A type of its own means blank slots, not the donor’s parts. Thirteen of twenty-one, on a typical weapon — and blank costs you nothing: the modification still gives its stats, the gun just does not change shape.
  • A blank-but-selectable row in a long weapon list is the game’s, not yours. Which row it is changes as you scroll. Making a weapon.
  • Your mod’s copies never touch the game’s art, shared attachment textures included. If something changed on a weapon you did not edit, it was not this.

Those ModSource folders are made for you the first time you import something, so you do not need to create them. A file left in a ModSource folder beside your mods folder, without your mod’s name in the path, is also found, which is the older layout from when mods lived inside an Unreal project.

The .json project file is plain text and safe to edit by hand — comments and fields the tool does not know are preserved. It is also the only way to reach the handful of things that have no button yet, and The project file: things that have no button yet lists them.
